# Архитектура FixFlow AI

## Текущий фундамент

- Next.js App Router и TypeScript.
- Исходный код находится в `src`, внутренние импорты используют `@/*`.
- Tailwind CSS и shadcn/ui отвечают за интерфейс.
- Vitest покрывает доменную и серверную логику.
- Neon PostgreSQL хранит данные приложения.
- Drizzle ORM описывает схему и выполняет запросы.
- Drizzle Kit создаёт и применяет SQL-миграции.
- Netlify остаётся целевой платформой размещения.

Claude Messages provider подключается опционально через server-only
конфигурацию. RAG и API внешних автоматизаций пока не подключены.

## Поток данных

```text
Браузер
  └─ Next.js
      ├─ клиентский чат
      ├─ публичная read-only CRM (/demo/crm)
      ├─ server-only слой Drizzle ORM
      │   └─ Neon PostgreSQL
      └─ исходящие webhook-события
          └─ Make
              ├─ Router по eventType
              ├─ Telegram
              └─ расписание отложенных автоматизаций
                  └─ POST /api/integrations/automation/scan
```

## Подключение к базе

- Приложение использует `DATABASE_URL` — pooled Neon connection string.
- Drizzle Kit использует `DATABASE_URL_DIRECT` — direct connection string для миграций.
- Обе переменные валидируются через Zod.
- Серверный env-модуль и подключение к базе защищены директивой `server-only`.
- Имена переменных не имеют префикса `NEXT_PUBLIC_`, поэтому Next.js не включает их в браузерный bundle.
- SQL-миграции хранятся в `drizzle/` и применяются командой `npm run db:migrate`.

## Модель данных

Данные разделены на четыре группы:

- каталог и знания: `services`, `documents`, `document_chunks`;
- клиенты и выезды: `customers`, `leads`, `availability_slots`, `bookings`,
  `tasks`;
- AI-диалог: `conversations`, `messages`, `ai_runs`;
- интеграции: `integration_events`, `automation_logs`.

Категории, статусы, приоритеты и источники с фиксированным набором значений
реализованы PostgreSQL enum. Диапазоны цен, длительность, порядок временных
границ и HTTP-статусы защищены check constraints.

Все моменты времени хранятся как `timestamp with time zone`; PostgreSQL
нормализует их к UTC. `preferred_date` и `preferred_time` — не момент времени,
а отдельно выбранные клиентом календарная дата и время, поэтому хранятся как
`date` и `time`.

Цены хранятся целыми числами в минимальных денежных единицах. Это исключает
ошибки округления чисел с плавающей точкой.

Каскадное удаление разрешено только для полностью зависимых записей:
сообщений диалога и чанков документа. Основные заявки, клиенты, слоты и
бронирования защищены `restrict`, а необязательные ссылки журналов и задач
обнуляются через `set null`.

## Демонстрационные данные

Канонический набор FixFlow Service создаётся только вручную командой
`npm run demo:seed`. Он содержит 12 услуг, 12 клиентов, 18 заявок, 20 будущих
слотов и 6 задач.

Каждая такая запись имеет `is_seed=true`, а клиент дополнительно имеет
`is_demo=true`. UUID детерминированы, а запись выполняется через PostgreSQL
upsert, поэтому повторный запуск обновляет те же строки и не создаёт дубликаты.

`npm run demo:reset` удаляет только строки с `is_seed=true` в безопасном
порядке зависимостей и запускает seed заново. Миграции содержат только
изменения схемы: seed никогда не выполняется автоматически и не смешивается с
ними.

В seed используются заведомо учебные телефоны с нерабочим кодом `+380 00`,
адреса вида «Демо-город / дом DEMO-XX», домен `example.com` и видимый префикс
`[ДЕМО]`.

## Проверка доступности

`GET /api/health/db` выполняет `SELECT 1`. При доступной базе endpoint возвращает:

```json
{
  "status": "ok",
  "database": "connected"
}
```

При ошибке возвращается HTTP 503 без connection string и внутренних деталей.

## Публичная CRM

Маршруты `/demo/crm`, `/demo/leads/[id]`, `/demo/knowledge`,
`/demo/ai-runs` и `/demo/automations` публичны и не содержат регистрации,
логина или операций записи.

Server Components читают Neon напрямую через server-only Drizzle-модуль.
Kanban получает первоначальные данные на сервере, а затем Client Component
обращается к публичному `GET /api/demo/leads` вручную и каждые 10 секунд.
Endpoint использует `Cache-Control: no-store`, поэтому новая заявка появляется
без production rebuild.

Публичные DTO не содержат сырых `phone`, `email` или `address`. Телефон
маскируется на сервере, адрес заменяется кратким названием локации, а тексты
сообщений и AI-сводок проходят дополнительное редактирование телефонов и
адресных фрагментов до сериализации.

Фильтры категории, статуса, приоритета и источника, а также поиск по номеру,
имени и описанию выполняются SQL-запросом к Neon. Kanban не содержит drag and
drop и не вызывает mutating API.

## Публичная форма заявки и бронирование

Маршрут `/request` читает активные услуги из Neon и передаёт их клиентскому
компоненту без строк подключения. Server Action повторно проверяет все поля
через Zod, нормализует демонстрационный телефон, сверяет услугу с каталогом и
применяет постоянный rate limit по SHA-256 ключу от IP и User-Agent. Сырые
идентификаторы посетителя в базе не хранятся.

UUID формы служит ключом идемпотентности. Клиент, заявка и запись о принятой
форме создаются через `neon-http` batch, который Neon выполняет одной
транзакцией. PostgreSQL sequence формирует номер `FF-1042`, а пользовательские
демо-записи получают `is_seed=false` и `expires_at` через 48 часов.

На `/request/success` доступны только свободные слоты той же категории.
Бронирование — один атомарный SQL statement с CTE: условно переводит слот из
`available` в `booked`, создаёт booking и меняет статус lead на `booked`.
Уникальные ограничения по lead и slot остаются вторым уровнем защиты от
конкурентного двойного бронирования.

На этом этапе форма не запускает AI и не создаёт webhook-события.

## Гибридный чат

`/chat` всегда опирается на детерминированный конечный автомат. Первый
`POST /api/chat/start` создаёт conversation и сохраняет описание проблемы
вместе с ответом ассистента. Последующие `POST /api/chat/message` читают
`current_step` и задают только первый недостающий вопрос.

Состояние хранится в `conversations.collected_data`, а каждое сообщение
клиента и ассистента — отдельной строкой `messages`. Для выбора категории,
услуги и времени API возвращает безопасные DTO в `options`; услуги и слоты
всегда читаются из Neon, а не из mock-массивов интерфейса.

После сбора желаемого времени один SQL statement блокирует строку conversation,
создаёт или обновляет demo-customer, создаёт lead с `source=ai_chat` и
связывает его с conversation. После выбора слота другой атомарный statement
условно захватывает только `available` слот, создаёт booking, меняет lead на
`booked` и завершает conversation. Уникальный индекс `bookings.slot_id`
остаётся дополнительной защитой от конкурентного бронирования.

Перед детерминированным переходом server-only LLM provider может вызвать Claude
Messages API. Модель классифицирует intent и category, извлекает только явно
названные поля и предлагает естественную формулировку вопроса. Сервер
валидирует JSON через Zod, повторно проверяет каждое извлечённое поле и сам
вычисляет следующий шаг. `proposedAction` никогда не исполняется напрямую.

Provider не получает соединение с Neon, tools или функции. RAG-контекст
формируется сервером после vector-поиска и передаётся provider как
неизменяемый список источников. Timeout классификации равен 7 секундам, а
ответа по RAG — 12 секундам. При неправильном
JSON, несовпадении схемы, низкой confidence, timeout, недоступности или
отсутствии конфигурации используется прежний детерминированный ответ.

Каждая попытка сохраняется в `ai_runs`: операция, модель, безопасная сводка
вида шага и длины сообщения, редактированный parsed output, длительность,
статус и безопасный код ошибки. API-ключ, полный prompt и необработанные
контактные данные не сохраняются.

## Границы ответственности

Next.js отображает чат и CRM, проверяет входные данные, маскирует персональные
поля, работает с Neon и отправляет webhook-события. Next.js не отправляет
Telegram-сообщения, не запускает cron, не держит таймеры и не выполняет
отложенный follow-up.

Make получает webhook-события и отвечает за Telegram, задержки, follow-up и
остальные внешние автоматизации. Отложенные сценарии Make вызывают
`POST /api/integrations/automation/scan`: Next.js только отвечает, какие
follow-up и напоминания наступили, и передаёт новые события в тот же outbox.
Полное описание контура находится в `docs/automations.md`.

## Данные и безопасность

- CRM публичная, доступна без логина и только для чтения.
- Используются исключительно вымышленные записи.
- Телефоны и адреса маскируются в интерфейсе и технических выводах.
- Секреты хранятся только в переменных окружения.
- `.env` и `.env.local` исключены из Git.
- Supabase и Vercel не используются.

## RAG и база знаний

`knowledge/demo` содержит только демонстрационные Markdown-документы. Команда
`knowledge:seed` принимает `.md` и `.txt`, разбивает текст на chunks примерно
по 700–1000 символов с overlap около 120 символов и создаёт локальные
детерминированные vectors размерности 1536. Они хранятся в
`document_chunks.embedding vector(1536)` и индексируются HNSW с
`vector_cosine_ops`.

Retrieval определяет категорию вопроса, ищет одновременно в ней и `common`,
отбрасывает similarity ниже порога и возвращает максимум пять chunks. Claude
получает только найденный контекст. Сервер отклоняет неподтверждённые числа,
пожизненную гарантию и обещание точной цены. При недостатке источников действие
принудительно меняется на `handoff_to_human`.
