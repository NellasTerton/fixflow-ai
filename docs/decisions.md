# Решения FixFlow AI

## D-001. Публичное портфолио-демо

FixFlow AI создаётся как публичная демонстрация навыков, а не как рабочая
система сервисной компании. Все сценарии и записи вымышлены.

## D-002. CRM без авторизации

Полноценной авторизации сотрудников пока нет. `/demo/crm` доступна без логина,
публично и только для чтения.

## D-003. Без реальных персональных данных

Настоящие персональные данные не используются. Демонстрационные телефоны и
адреса маскируются в интерфейсе, логах и технических выводах.

## D-004. Автоматизации находятся вне Next.js

Next.js только отправляет webhook-события. Он не отправляет сообщения в
Telegram, не запускает cron, таймеры или отложенный follow-up. За Telegram,
задержки и внешние автоматизации отвечает Make. n8n не используется.

## D-005. Платформы

Приложение готовится к размещению на Netlify. Supabase и Vercel не
используются.

## D-006. LLM и внешние API отложены

LLM, RAG-провайдер и внешние API пока не подключаются. Они будут добавляться
отдельными этапами.

## D-007. Neon PostgreSQL и Drizzle

Neon PostgreSQL выбран как хранилище данных. Приложение подключается через
`@neondatabase/serverless` и Drizzle ORM. Схема и история миграций находятся в
репозитории, а секреты — только в переменных окружения.

## D-008. Раздельные подключения приложения и миграций

Next.js использует pooled `DATABASE_URL`. Drizzle Kit использует
`DATABASE_URL_DIRECT` только для миграций и Drizzle Studio. Серверные env-модули
защищены `server-only`; connection strings не передаются клиентскому коду.

## D-009. Строгая реляционная модель демо

Основные категории и статусы хранятся как PostgreSQL enum, а допустимые
диапазоны контролируются check constraints. Цены записываются целыми числами в
минимальных денежных единицах. Все моменты времени используют `timestamptz` и
интерпретируются как UTC.

Исторические сущности не удаляются каскадом. `cascade` применяется только к
сообщениям конкретного диалога и чанкам конкретного документа; для
необязательных ссылок используется `set null`.

`integration_events.entity_id` остаётся полиморфным идентификатором: событие
может относиться к разным типам сущностей, поэтому один обычный внешний ключ
PostgreSQL для него невозможен. Все однозначные связи модели защищены внешними
ключами.

## D-010. Seed отделён от миграций

Демонстрационные записи создаются только явными командами `demo:seed` и
`demo:reset`. Миграции не содержат данных и не запускают seed.

Канонические записи получают детерминированные UUID и `is_seed=true`, поэтому
upsert идемпотентен, а reset может удалить только известный seed-набор. Любые
строки без seed-маркера остаются нетронутыми.

Для клиентов используются только явно вымышленные имена, нерабочие
демонстрационные телефоны, адреса в Демо-городе и email на `example.com`.

## D-011. Публичная CRM остаётся read-only

Все `/demo/*` маршруты доступны напрямую без регистрации и логина. Интерфейс
не содержит форм редактирования, drag and drop или mutating endpoints.

Первый рендер читает Neon на сервере, а Kanban обновляется через публичный
`GET /api/demo/leads` с `no-store` каждые 10 секунд. Это позволяет показывать
новые заявки из будущего AI-чата без rebuild.

Публичный API возвращает только специально сформированные DTO. Точные адреса и
сырые телефоны не передаются в браузер; маскирование и редактирование текстов
происходит на серверной границе.

## D-012. Публичная заявка безопасна и идемпотентна

Форма принимает только явно демонстрационные телефоны и общую локацию без
точного адреса. Проверка Zod выполняется на сервере независимо от браузерных
ограничений. Защита состоит из honeypot, постоянного rate limit в Neon,
отключения кнопки во время отправки и уникального UUID-ключа идемпотентности.

Neon HTTP не поддерживает интерактивные транзакции Drizzle, поэтому создание
customer, lead и form submission выполняется официальным `db.batch`, который
отправляет команды в одну Neon-транзакцию. Бронирование реализовано одним
атомарным PostgreSQL statement с условным захватом слота. Этот выбор сохраняет
HTTP runtime без WebSocket, Pool и Client.

Номера заявок выдаёт sequence, начиная с `FF-1042`. Пользовательские
демо-записи не относятся к seed и автоматически помечаются сроком жизни 48
часов. AI и webhook в этом этапе не вызываются.

## D-013. Первый чат — детерминированный конечный автомат

До подключения LLM клиентский чат использует фиксированный порядок полей и
состояние `current_step`. Это делает поведение воспроизводимым, позволяет
проверить полный продуктовый путь и исключает выдуманные моделью категории,
услуги или слоты.

API принимает только текущее сообщение и UUID conversation. Сервер повторно
валидирует значение в контексте текущего шага, а варианты категорий, услуг и
слотов формирует сам. Клиент не определяет следующий шаг и не может передать
цену, статус или источник заявки.

Создание lead и финальное бронирование выполняются атомарными PostgreSQL
statement с блокировкой conversation. Такой подход совместим с Neon HTTP и
защищает диалог от повторного создания заявки и двойного бронирования без
WebSocket-транзакций.

## D-014. LLM предлагает, сервер решает

Claude используется только как ограниченный языковой слой: определяет intent и
category, извлекает структурированные значения и предлагает текст следующего
вопроса. Provider не получает tools, доступ к базе или функции создания и
бронирования.

Ответ должен пройти строгую Zod-схему и порог confidence 0.7. Даже валидное
`proposedAction` не исполняется: конечный автомат независимо выбирает
разрешённый переход. При любой ошибке используется детерминированный сценарий,
поэтому доступность внешнего provider не влияет на возможность оформить
заявку.

В `ai_runs` сохраняется минимальная техническая трассировка. Полный prompt и
API-ключ запрещены, input summary содержит только шаг, длину сообщения и
количество RAG-чанков, а извлечённые контакты редактируются.

## D-015. Локальные embeddings для публичного демо

Claude API не предоставляет собственную embedding-модель, а отдельный внешний
embedding-провайдер и новый секрет не входят в текущий этап. Поэтому FixFlow
использует версионированный локальный детерминированный embedding
`fixflow-local-hash-v1` размерности 1536. Neon/pgvector выполняет реальный
cosine-поиск и HNSW-индексацию.

Документы seed-ятся отдельно от миграций. Повторный запуск заменяет chunks
одного документа и не создаёт дубликаты. Production embedding provider позднее
можно подключить без изменения retrieval-контракта.

## D-016. Отложенные автоматизации — расписание в Make, решение в SQL

Follow-up по заявке без бронирования и напоминание перед выездом реализованы
без cron, таймеров и очередей внутри Next.js. Планировщиком остаётся Make:
сценарий `FixFlow AI — Delayed automations` раз в 15 минут вызывает
`POST /api/integrations/automation/scan`.

Endpoint не хранит состояние и не спит. Он детерминированно отвечает на вопрос
«какие отложенные события наступили прямо сейчас», создаёт события
`lead.followup_due` и `booking.reminder_due` и передаёт их в тот же outbox, что
и мгновенные события. Поэтому отложенные уведомления идут через тот же Custom
Webhook, тот же Router и тот же callback.

Пороги передаются Make и валидируются сервером в безопасных границах, а
значения по умолчанию (30 и 120 минут) заданы в коде. Seed-заявки исключены из
выборки, иначе первый запуск отправил бы 18 сообщений по демонстрационным
данным.

Повторную отправку исключает уникальный индекс
(`event_type`, `entity_type`, `entity_id`) в `integration_events`: у заявки
может существовать только один follow-up и только одно напоминание. SQL
дополнительно отбрасывает уже обработанных кандидатов, поэтому повторный запуск
сканирования ничего не отправляет.

Сканирование защищено тем же общим секретом, что и callback, но отдельным
заголовком `x-fixflow-automation-secret`. Новая переменная окружения не
понадобилась.

## D-017. Маршрутизация Make строго по eventType

Каждая ветка Router фильтруется точным сравнением `eventType`. Ветки без
фильтра, fallback-маршруты и фильтры по `urgency` запрещены: `urgency=normal`
совпадает с четырьмя типами событий из пяти и приводит к двойным
Telegram-уведомлениям.

Каждая ветка отправляет callback со своим значением `action`. Уникальный индекс
`automation_logs` по (`integration_event_id`, `platform`, `workflow_name`,
`action`) иначе схлопнул бы два вызова в одну строку, и лишняя ветка осталась бы
невидимой в `/workspace/automations`.

## D-018. Репозиционирование: рабочее пространство поверх demo-данных

FixFlow AI переставал читаться как рабочий продукт: слово «демо» и
предупреждение «read-only» повторялись почти на каждом экране, а публичные
маршруты жили под `/demo/*`. Архитектура была в порядке — упаковка выглядела
как учебная демонстрация, а не как продукт, который можно было бы поставить.

Маршруты переименованы: `/demo/crm` → `/workspace/leads` (более точное имя —
раздел показывает заявки, а не полноценную CRM), `/demo/knowledge` →
`/workspace/knowledge`, `/demo/ai-runs` → `/workspace/ai-runs`,
`/demo/automations` → `/workspace/automations`, `/demo/leads/[id]` →
`/workspace/leads/[id]`. Старые пути отдают постоянный redirect в
`next.config.ts`, поэтому уже сохранённые ссылки не ломаются.

Два отдельных предупреждения о demo-режиме на каждой странице рабочего
пространства заменены одной строкой: «Вы находитесь в тестовом рабочем
пространстве FixFlow Service. Данные вымышлены.» Главная страница описывает
продукт в терминах бизнеса («AI-диспетчер и операционная система для выездных
сервисных компаний»), а не как демонстрацию портфолио; технические
доказательства (RAG, AI runs, webhook, Make) остаются на своих страницах, но
не выносятся в заголовок.

Это меняет **формулировку** D-001, но не её суть: продукт по-прежнему
работает только с вымышленными данными, реальные персональные данные
запрещены, а публичное рабочее пространство остаётся без авторизации
сотрудников и без операций записи — оба свойства подтверждены D-002 и D-011 и
не отменяются этим решением.

Отдельно обсуждалась и была сознательно отложена идея sandbox-надстройки:
анонимная cookie-сессия, позволяющая посетителю менять статус заявки,
добавлять комментарии и задачи только в рамках своего браузера, с истечением
через несколько часов — по аналогии с уже существующим TTL для заявок и
клиентов из формы. Схема (три новые таблицы, сессия, rate limiting) была
спроектирована, но не реализована: интерактивность продукта уже полноценно
показана через чат, реальное бронирование и появление заявки в CRM, а
дополнительная инженерная поверхность не оправдывала себя для этого этапа.
Если понадобится, дизайн можно поднять заново, не переизобретая его с нуля.

## D-019. Первая правка репозиционирования: убрать «демо» из данных и с
поверхности, а не только из заголовков

После D-018 стало ясно, что заголовков и баннеров недостаточно: рабочее
пространство всё равно выглядело как учебная демонстрация по трём причинам,
не связанным с текстом страниц.

Во-первых, сервер помечает каждое имя клиента, адрес и описание проблемы
буквальным тегом `[ДЕМО]` перед записью в Neon — это осознанная защита
(D-003): даже если посетитель введёт похожее на настоящее имя, в сырых
данных, логах и Telegram-уведомлениях оно останется однозначно вымышленным.
Но тег утекал и в публичный интерфейс: карточка заявки показывала буквально
«[ДЕМО] Иван Петров». Добавлена `stripDemoTag` — тег убирается только при
публичном отображении (`toPublicLead`), а в исходной строке, экспорте и
Telegram остаётся как и раньше.

Во-вторых, `leads.expires_at` — 48-часовой TTL для заявок, отправленных через
форму и чат — записывался при создании, но никогда не проверялся при чтении.
`listPublicLeads`/`getPublicLeadDetail` показывали вообще все заявки,
включая протухшие тестовые с посторонним текстом («Демо-протечка»,
«демонстрационной зоне»), накопленные за время разработки. Добавлено
условие: заявка видна, если она из seed или срок ещё не истёк
(`is_seed = true or expires_at is null or expires_at > now()`) — seed-данные
не задеты, потому что у них тоже стоит `expires_at`, но только для
`demo:reset`, а не для публичного показа.

В-третьих, «AI runs» и «Автоматизации» были равноправными вкладками рядом с
«Заявки» и «База знаний» — то есть техническая обсервability оказалась в
одном ряду с бизнес-разделами. `workspaceNavigation` получил поле `tier`:
«Заявки»/«База знаний» остаются основной навигацией, «AI runs»/
«Автоматизации» показаны отдельно и приглушённо — доступны тем же одним
кликом, но не соревнуются за внимание.

Отдельно с главной страницы убраны секции «Как оценить продукт за 3 минуты»
и «Без чата — заглянуть внутрь»: они были рассчитаны на человека, оценивающего
портфолио, а не на посетителя продукта. Краткая инструкция «как быстро
попробовать» перенесена в `README.md`.

## D-020. Лендинг реальной компании и пайплайн из пяти статусов

Правки D-019 сняли слово «демо» с интерфейса, но продукт всё ещё читался как
учебная модель, потому что нетронутыми остались данные, пайплайн и сама
главная страница.

**Сид переписан целиком.** Клиентов звали «Алиса Макетова», «Борис
Тестовский», «Мирон Портфолиев» — фамилии буквально означали «макет», «тест»,
«портфолио», а описания проблем были вида «Учебная стиральная машина не
завершает цикл». Теперь это обычные имена, реальные районы Киева и живые
описания неисправностей. Единственное, что осталось намеренно ненастоящим, —
телефонный диапазон `+380 00`: этот код не выделен ни одному оператору, то
есть ни один номер в базе физически не может дозвониться до человека. Это и
есть настоящая гарантия безопасности, в отличие от подписи «[ДЕМО]», которая
только портила вид.

**Цены перестали быть случайными.** Раньше у заявки был свой произвольный
`estimate`, никак не связанный с прайсом услуги, и диапазон висел даже на
выполненной заявке. Теперь оценка выводится из опубликованного диапазона
услуги (`estimateFor`), а у выполненных работ `estimatedPriceFrom` равен
`estimatedPriceTo` — это фактическая сумма, и интерфейс подписывает её как
«итог», а не «оценка». `formatPriceRange` больше не печатает «1 800–1 800 ₴».

**Статусов стало пять вместо восьми.** `qualifying` и `waiting_booking` оба
означали «ещё не запланирована» и различались только тем, на каком шаге чата
заявка застряла — это внутреннее состояние диалога, а не стадия работы
компании. `human_required` вообще не стадия, а признак: заявка остаётся
новой, просто ей нужен человек. Он стал колонкой `leads.needs_operator` и
показывается меткой на карточке. Пайплайн: `new → booked → in_progress →
completed / cancelled`.

Миграция `0006` написана вручную: сгенерированная Drizzle версия приводила
колонку обратно к enum до того, как старые значения были переписаны, и упала
бы на существующих строках. Порядок обязателен — сначала добавить и заполнить
`needs_operator`, потом переписать статусы в text, и только затем заменять
тип.

**AI runs и автоматизации убраны из навигации.** Это инструменты разработчика,
а не разделы, в которых работает диспетчер. Страницы остались доступны и
по-прежнему связаны с конкретной заявкой, где такая трассировка уместна.

**Главная страница переписана как лендинг сервисной компании.** Вместо
заголовка «Заявка на выезд без потерянных деталей» и двух одинаковых кнопок
«Открыть рабочее пространство» — обычный лендинг: оффер, гарантии, прайс из
той же таблицы `services`, что цитирует чат, и встроенный в hero рабочий чат
с диспетчером. Логика диалога вынесена в `useChatSession`, поэтому виджет на
главной и страница `/chat` используют один и тот же конечный автомат и одни
и те же endpoint'ы.

В подвале осталась одна строка о том, что компания и заявки вымышленные, а
телефоны нерабочие. Она не мешает первому впечатлению, но снимает риск, что
посетитель примет публичную базу за боевую систему с живыми клиентами и
введёт настоящие данные.

## D-021. Москва и рубли вместо Киева и гривны

Сид был собран вокруг Киева (районы, гривна), а пользователь попросил
переделать под российский город. Смешивать валюту одной страны с районами
другой — та же ошибка, что уже была с ценами и статусами: две несвязанные
детали, которые выдают несерьёзность продукта при первом внимательном
взгляде.

Выбрана Москва: 12 клиентов получили настоящие районы (Тверской, Басманный,
Хамовники, Останкинский, Митино, Строгино, Бибирево, Марьино, Кузьминки,
Царицыно, Чертаново, Ясенево). `formatPriceRange` печатает ₽. `service-area.md`
переписан с вымышленных «Северный/Южный/Центральный/Прибрежный demo-районов»
на «Москва в пределах МКАД» — RAG-документ должен соответствовать реальным
районам клиентов, иначе диспетчер расходится с собственной базой.

Формат телефона тоже пришлось менять, а не только валюту и районы: `+380 00`
— это украинский код, оставлять его при переезде в Москву было бы точно той
же нестыковкой. Новый безопасный диапазон — `+7 000`: блок «000» не
распределён ни одному российскому оператору, поэтому ни один номер в базе
физически не может дозвониться до человека. Это тот же приём, что и раньше,
просто под правильную страну. Правки прошли через нормализацию телефона,
regex-валидацию на клиенте и в чате, маскирование и redaction-паттерн для
текста заявок — все места, где раньше было зашито `380`.

## D-022. Маркер безопасности базы знаний остаётся в файле, но не в эмбеддинге

`knowledge:seed` требует строку «Демонстрационные данные вымышленной
компании» в каждом исходном файле — это защита от случайного добавления
контента настоящей компании в RAG. Но чанкер встраивает файл как есть, без
удаления markdown-разметки, поэтому эта же строка утекала в чанки и могла
попасть в ответ клиенту, если RAG её процитирует. Ровно та же категория
проблемы, что и `[ДЕМО]`-тег в данных заявок, только на уровне базы знаний.

Решение: маркер остаётся обязательным в исходном `.md`-файле (проверка при
сборке не убрана), но `knowledge-seed.ts` вырезает эту строку перед
чанкингом и эмбеддингом. Разработчик по-прежнему обязан сознательно
подтвердить, что файл содержит вымышленный контент; посетитель и AI этот
маркер никогда не увидят.

Заодно переписаны все 12 файлов `knowledge/demo/*.md`: убраны
«демонстрационную/условную/вымышленную» формулировки из текста, который
реально цитирует чат при ответах о ценах, гарантии и зоне обслуживания.

## D-023. Диалог не должен объяснять свои же ограничения, а подбор услуги
должен реагировать на то, что сказал клиент

После продуктового прохода нашлись три вещи глубже, чем формулировки.

**«Используйте вымышленное имя» — лишнее повторение.** Предупреждение о
безопасности уже показано один раз: в боковой панели `/chat` и подписи под
hero-виджетом на главной. Повторять его в каждом диалоге как часть вопроса
«Как к вам обращаться?» — тот же анти-паттерн, что и demo-баннеры на каждой
странице, только внутри разговора. Убрано из обоих мест, где формировался
этот вопрос (`workflow.ts`); предупреждение осталось только в двух
персистентных местах интерфейса — сайдбар полного чата и подпись под
hero-виджетом (её раньше не было вовсе).

**Подбор услуги игнорировал собственный ответ LLM.** `startChatWorkflow`
подставлял естественную формулировку модели (`naturalQuestion`) только для
`action === "ask_question"`, а переход `show_services` всегда получал
жёсткую строку «Выберите тип услуги или техники.» — даже когда модель уже
разобрала описание проблемы и предложила осмысленный контекстный ответ.
Из-за этого диалог выглядел так, будто он не понял, что ему написали, хотя
классификация внутри уже отработала. Условие расширено на `show_services`;
`naturalQuestion` и так проверяет длину, наличие «?» и отсутствие ссылок —
в худшем случае просто ничего не меняется.

**Установки бытовой техники не было в каталоге.** Клиент спросил
«можете установить стиральную машинку» — фаззи-матчинг (`validateChatExtraction`)
не нашёл совпадения, потому что такой услуги не существовало вообще: у
техники были только четыре позиции «Ремонт ...». Диспетчер показывал все
доступные ремонты, что выглядело как нерелевантный список кнопок. Добавлена
услуга «Установка бытовой техники» (`services-appliances.md`,
`prices-appliances.md`, сид) — это устраняет проблему по существу, а не
только меняет форму отказа.

Системный промпт классификации в `llm-orchestrator.ts` тоже переписан: он
называл продукт «a public fictional field-service demo» — сама модель не
должна думать о себе как о демо-заглушке, даже если эта фраза никогда не
видна пользователю. Заменено на прямое описание роли: AI-диспетчер
сервисной компании в Москве.

## D-024. Переезд production-хостинга с Netlify на Vercel

Оба фикса из D-023 (`show_services` подхватывает ответ LLM, новая услуга
установки) были закоммичены и запушены в `main`, но при повторной проверке в
production поведение не менялось — диспетчер по-прежнему отвечал жёсткой
строкой. Диагностика через прямой SQL-запрос к `ai_runs` показала, что LLM
всё это время классифицировал запросы правильно (`status: "success"`,
`proposedAction: "ask_question"`, осмысленный `reply`) — то есть баг был не
в коде.

Причина оказалась инфраструктурной: Netlify-проект `fixflow-ai-661` исчерпал
месячный лимит credits (Free-план, 300/мес — 20 production-деплоев съели все
300 разом, это единственный компонент, забравший главный лимит). Netlify
после исчерпания ставит **production-деплои на паузу**, но опубликованный
сайт продолжает отвечать на старой, последней успешно собранной версии —
внешне неотличимо от «код не изменился». Каталог услуг в проде при этом
обновлялся (сиды идут напрямую в Neon через `npm run demo:seed`, это отдельный
канал от деплоя приложения), из-за чего новая услуга уже была видна, а
логика ответа — нет. Подтверждено: `.netlify/deploy` последний раз
пересобирался 2026-07-30 16:35, то есть до обоих коммитов с реальным фиксом
(2026-08-02).

Решение — перенос на Vercel, подключённый напрямую к GitHub-репозиторию
(`Import Git Repository` в Vercel dashboard), а не через прямую заливку
файлов: это восстанавливает автодеплой по `git push`, который на Netlify
физически не отработал из-за паузы. У MCP-инструментов Vercel в этой сессии
нет способа программно создать env-переменные проекта — только сборка из
файлов без git и просмотр/защита существующего проекта. Импорт репозитория и
первичная вставка `.env` в форму создания проекта — шаг, который выполняет
только пользователь (OAuth-разрешение GitHub → Vercel через браузер).
Секреты `AUTOMATION_WEBHOOK_SECRET`/`AUTOMATION_CALLBACK_SECRET` перенесены
как есть (сняты с Netlify Environment Variables), чтобы не трогать рабочий
Make-сценарий — генерировать новые значения означало бы синхронно менять и
сторону Make, а это отдельный риск сломать доставку в Telegram без выигрыша.

Живой продукт теперь на `https://fixflow-ai-kappa.vercel.app`. Ссылки в
README/docs обновлены (кроме исторической записи о верификации Netlify-путей
в `docs/progress.md` — старые логовые записи не переписываются задним числом).

## D-025. Убрана LLM-подстановка вопроса на каждом шаге диалога — она ломала
сбор данных, а не просто звучала не идеально

После переезда на Vercel и повторного прохода вживую (реальный браузер,
несколько ходов подряд, а не только первый запрос к `/api/chat/start`)
вскрылась серьёзная регрессия из D-023: расширение подстановки
LLM-формулировки на `show_services`, в сочетании с уже существовавшим
(с более раннего периода) пробросом `assistantReply` в `continueChatWorkflow`
на каждом шаге сбора полей (`service` → `name` → `phone` → `area` →
`preferred_date`), приводило к двум разным поломкам:

1. **Несовпадение вопроса и формы ответа.** На переходе `show_services`
   LLM формулирует открытый диагностический вопрос («как проявляется
   поломка?»), пока интерфейс одновременно показывает кнопки выбора
   услуги — клиенту предлагают одновременно печатать текст и жать кнопку.
2. **Пропуск обязательного вопроса с порчей данных.** Хуже: на шаге
   `service → name` (после выбора услуги кнопкой) LLM-анализ конкретного
   сообщения без истории диалога (`analyze()` получает только текущий шаг,
   `missingFields` и последнее сообщение — не полную историю) иногда
   придумывал не относящийся к делу вопрос («в каком помещении и какая
   площадь у кондиционера?») и подставлял его ВМЕСТО детерминированного
   «Как к вам обращаться?». Ответ клиента на этот случайный вопрос
   (например «не знаю») проходил валидацию `nameSchema` (она проверяет
   только длину, не смысл — см. D-023) и молча записывался в поле
   `demoName`. То есть терялся не только вопрос, но и корректность данных
   заявки.

Корневая причина архитектурная: `naturalQuestion()` проверял только форму
предложенного текста (есть «?», нет URL, не длиннее 500 символов), но не
то, отвечает ли он вообще на тот вопрос, который в этот момент задаёт
детерминированный автомат. LLM в `continueChatWithLlm` не видит полной
истории диалога — только текущий шаг и одно сообщение, — поэтому не может
надёжно отслеживать, какое именно поле сейчас собирается.

Решение — полностью убрать LLM-формулировку из пользовательских вопросов
`workflow.ts`: `naturalQuestion()`, `ChatTurnGuidance`, `assistantReply` в
`ChatStartGuidance` и `approvedNaturalReply()` в `llm-orchestrator.ts`
удалены целиком, а не просто отключены. Каждый шаг диалога всегда
использует свой фиксированный детерминированный текст — на первом ходу
(`show_categories`/`show_services`) и на всех последующих шагах сбора полей.
LLM по-прежнему классифицирует проблему, извлекает category/serviceType и
структурированные данные (это остаётся, сервер по-прежнему независимо
валидирует каждое поле) — просто больше не формулирует сам текст вопроса.
Компромисс: диалог теряет контекстную реплику-подтверждение первого хода
(«Похоже, нужна помощь со стиральной машиной») ради надёжности — при
текущей архитектуре (без полной истории в LLM-анализе) это была не
косметическая недоработка, а источник реальной порчи данных.

## D-026. Реальный телефон вместо поддельного формата + LLM-маршрутизация
услуги с честным fallback «Выезд и диагностика»

Владелец прошёл диалог вживую и указал на две вещи, делающие бота
бесполезным: (1) форма требовала поддельный номер `+7 000...` и отвергала
реальный телефон; (2) подбор услуги через фиксированные кнопки ограничивал
клиента — нужного варианта часто нет («поменять сифон + заменить раковину»),
а на «кран течёт» бот вываливал весь список вместо понимания. Оба решения
согласованы с владельцем через AskUserQuestion.

**Телефон.** `DEMO_PHONE_PATTERN` (`/^\+7000\d{7}$/`) заменён на обычный
российский валидатор `RUSSIAN_PHONE_PATTERN` (`/^\+7\d{10}$/`);
`normalizePhone` теперь приводит ведущую 8 и голый десятизначный номер к
`+7...`. Номера хранятся как введены — владелец сознательно принял, что на
публичной доске могут появиться реальные номера (после явного предупреждения
про ПД). Видимое предупреждение «не указывайте настоящие данные» в чате и на
форме оставлено намеренно: раз сбор реальных данных возможен, посетитель
должен видеть, что это тестовый диспетчер. Маскирование для Telegram
(`maskPhone`) не тронуто.

**Услуга.** Вместо хрупкого подстрочного матчинга каталог (13→16 позиций)
теперь встроен прямо в системный промпт LLM: модель обязана вернуть
`serviceType` дословно из списка нужной категории, понимая слова клиента
(«кран течёт» → «Замена смесителя»), а при неоднозначности/мульти-запросе/
неуверенности — «Выезд и диагностика». Детерминированный код по-прежнему
валидирует, что имя есть в каталоге этой категории, и владеет записью.
Ключевое решение по escape-hatch: «Выезд и диагностика» — это **реальная**
позиция каталога в каждой из трёх категорий (честная услуга выездной
компании: 500–900 ₽, засчитывается в ремонт), а не техническая заглушка.
Это значит, что заявка всегда создаётся через существующий транзакционный
`createLeadTurn` **без единого изменения SQL** — никакого serviceless-лида и
рискованной операции на CTE создания заявки. Услуга легитимно попадает в
витрину цен и RAG (обновлены `services-*`/`prices-*` документы). Когда LLM
уверенно подобрал услугу, первый ответ детерминированно подтверждает её по
провалидированному имени из каталога («Понятно — оформляю «...».») — это
даёт ощущение «бот понял», не возвращая LLM-формулировку из D-025.

## D-027. Reseed чистит bookings — иначе бронирование падало с 503

При сквозной проверке чат→бронь на проде последний шаг (выбор слота) стабильно
отдавал 503. Диагностика: 503 — это собственный catch маршрута
`/api/chat/message`, то есть внутри `continueChatWithLlm` бросалось исключение.
Прямой вызов `createBookingTurn` проходил, а полный путь оркестратора локально
воспроизвёл настоящую ошибку Postgres: `duplicate key value violates unique
constraint "bookings_slot_id_unique"` (код 23505).

Причина — не в коде диалога, а в сиде: `applyDemoSeed` (`demo:seed`) сбрасывает
статус всех слотов обратно в `available`, но таблицу `bookings` не трогает.
Брони, созданные раньше (в т.ч. на прежнем Netlify-проде — Neon-БД общая),
оставались висеть на тех же slot ID. При повторном бронировании такого слота
срабатывал уникальный ключ `slot_id`. Тот же FK от `bookings` к
`availability_slots`/`leads` объяснял, почему `demo:reset` вообще падал (нельзя
удалить слоты, пока на них ссылаются брони).

Исправление на двух уровнях: (1) данные на проде — удалены 7 висячих броней,
освобождённые слоты возвращены в `available`; (2) код — в `DemoSeedStore`
добавлен `clearBookings()`, `applyDemoSeed` чистит брони перед сбросом слотов,
а `clearSeedData` удаляет брони первыми (до слотов и лидов), что чинит и
`demo:reset`. Брони — это runtime-артефакты, а не seed-данные, поэтому reseed
их обнуляет, приводя демо в консистентно бронируемое состояние.

## D-028. Два ложных отказа: RAG резался лимитом ответа, маршрутизация — гейтом confidence

Владелец прошёл чат и прислал два бесящих кейса, оба — ложные отказы, где бот
знал ответ, но выбрасывал его.

**RAG говорил «недостаточно данных», показывая при этом источники с ценами.**
Диагностика (воспроизведено локально с сырым выводом модели): LLM выдавал
корректный обоснованный ответ с ценой и оговоркой про диапазон, но длиной
~660 символов, а `llmStructuredOutputSchema.reply` был ограничен 600 →
`invalid_schema` → ответ выбрасывался → handoff, хотя чанки нашлись (57%).
То есть хороший ответ убивался из-за нескольких лишних символов. Лимит поднят
до 1200 (chat-reply короткий и вообще не показывается после D-025, так что
запас влияет только на RAG-консультацию), плюс в RAG-промпт добавлено
требование быть кратким (≤4 предложений).

**Короткий сленг не маршрутизировался.** «не работает кондей» модель
классифицировала верно (air_conditioning, «Диагностика кондиционера»,
intent=service_request), но с confidence 0.6 < 0.7 (D-014) → весь вывод
отбрасывался → клиент падал на стену кнопок категорий. Решение: для
маршрутизации чата классификация используется даже при low_confidence
(`usableClassification`) — детерминированный матчинг каталога в
`validateChatExtraction` остаётся настоящей защитой, а неудачный матч просто
деградирует в кнопки, не хуже прежнего. Порог 0.7 сохранён для настоящих сбоев
(битый JSON, таймаут, неверная схема) и для RAG-грудинга. ai_runs по-прежнему
честно логируют low_confidence для наблюдаемости.

## D-029. RAG больше не тупиковая ветка — диалог всегда возвращает контроль
детерминированному автомату

Владелец прогнал чат вживую и упёрся в три сломанных момента подряд:
публичная панель «Источники ответа» с сырыми markdown-чанками
(`# Заголовок`, `[1][2]`) прямо в разговоре с клиентом; RAG-ответ, на
уточняющий вопрос которого клиент отвечает, а бот вместо продолжения
разговора пытается распарсить этот ответ как выбор категории и падает в
«Выберите категорию кнопкой ниже.»; и один и тот же смысл («установить
раковину»), маршрутизируемый в два несвязанных пути в зависимости только от
формулировки. Итог: «с ним невозможно общаться».

Причина — не косметика, а архитектурная: в чате живут две несвязанные
подсистемы. Детерминированный автомат (`workflow.ts`) ведёт `currentStep` и
собранные поля и работает надёжно сам по себе (это не пересматривается — см.
D-013/D-014). RAG (`llm-orchestrator.ts` + `rag/answer.ts`) подключён сбоку:
`answerWithRag` получает только текст вопроса, без шага и без собранных
данных, и не может вернуть управление обратно. Конкретно:
`startKnowledgeConversation` жёстко ставил `currentStep: "category"` и
`options: []` для RAG-старта; следующее сообщение клиента (даже реальный
ответ на настоящий вопрос автомата) не имело кнопок, летело в
`continueChatWorkflow`, который читал `currentStep: "category"` и пытался
распарсить его как категорию — всегда безуспешно. Каждый RAG-ход
внутри диалога сохранял `nextStep: conversation.currentStep` (это верно —
RAG-реплика не должна пропускать обязательное поле), но ответ клиенту состоял
**только** из текста RAG-ответа: `knowledgeResponse()` всегда возвращал
`options: []` независимо от того, что автомат на самом деле ещё ждёт. Для
шага с кнопками (категория/услуга) это тупик.

Решение: `determineNextPrompt` в `workflow.ts` уже была ровно той функцией,
что нужна — чистая функция от собранных данных, не зависящая от того, что
буквально записано в `currentStep`. Экспортирована как `resolvePendingPrompt`
и стала единым источником истины «что клиенту ещё нужно сделать». Теперь
после любого RAG-ответа (и на старте диалога, и посреди сбора полей) сервер
пересчитывает реальный следующий шаг через эту функцию и склеивает ответ:
текст RAG-консультации, пустая строка, затем настоящий вопрос автомата — с
его настоящими кнопками/действием. `useChatSession` рендерит их так же, как
для обычного шага, диалог больше не обрывается. Склейка не применяется при
целевом handoff человеку (`answer.status !== "success"`) — не имеет смысла
приглашать кликать по кнопкам сразу после «передаю диспетчеру», это уже
финальное состояние UI. Также не применяется на шагах `slot`/`complete`
(там уже создан лид/бронь, все поля собраны — `resolvePendingPrompt` в этом
случае ошибочно перескочил бы обратно на «Какое время…»; это редкий
краевой случай, не тот, что был воспроизведён, поэтому оставлен как раньше).

Отдельно при верификации всплыл смежный, но самостоятельный баг:
`isExpectedStepAnswer` для шагов `name`/`area` проверял только длину строки
(в отличие от `phone`/`preferred_date`/`preferred_time`, у которых есть
настоящий формат) — вопрос «какая у вас гарантия на ремонт?», заданный на
шаге «район», проходил эту проверку и **тихо сохранялся как район**, ровно
тот же класс порчи данных, что уже чинился в D-025. Добавлена проверка
`looksLikeQuestion` (наличие «?») для этих двух шагов — без нужды трогать
`isKnowledgeQuestion`/маршрутизацию, которая осталась как есть в этом заходе
(различие «сколько стоит X» vs «можете сделать X» — по сути легитимное
разное намерение реального диспетчера, а не баг; путаницу создавал именно
тупик RAG-ветки, который эта правка устраняет).

Публичная панель «Источники ответа» (`chat-client.tsx`) удалена из
клиентского виджета целиком — источники остаются во внутренней трассировке
`/workspace/ai-runs` (`saveRagAiRun` не тронут), но больше не показываются
посетителю как сырые markdown-чанки с цитатами.

## D-030. Кнопки убраны целиком — категория/услуга/слот теперь только
свободным текстом

Сразу после D-029 владелец упёрся в новую версию той же проблемы: RAG-ответ
уже сам задал уточняющий вопрос («Когда вам удобно, чтобы мастер приехал?»),
а следом автомат подряд задал ВТОРОЙ, противоречащий вопрос с кнопками («К
какому направлению относится проблема? Выберите вариант»). Решение —
перестать чинить кнопки и убрать их совсем: «Пусть будет без кнопок
реализован процесс консультации + записи». Согласовано через EnterPlanMode
до правок, поскольку это меняет предохранитель из D-013 (кнопки были
единственным способом гарантировать, что категория/услуга/слот — валидные
значения из каталога, а не выдумка модели или опечатка клиента).

**Категория и услуга** переведены на тот же паттерн, что уже был у услуги
(D-026): детерминированный матчер решает, LLM только предлагает кандидата.
`handleCategory` теперь пробует по очереди: точное enum-значение (на случай
если что-то всё ещё пришлёт его буквально) → `determineKnowledgeCategory`
(тот же regex-классификатор, что уже использует RAG, `rag/category.ts`) по
сырому тексту клиента → LLM-подсказка (категория, которую уже вернул
основной классификатор на этом же ходу) — но LLM-подсказка тоже обязана
совпасть с одной из трёх бронируемых категорий, иначе игнорируется.
`handleService` получил тот же трёхступенчатый матчинг с общим хелпером
`matchServiceByName` (вынесен из `validateChatExtraction`, чтобы кнопочный
id, сырой текст клиента и LLM-подсказка сверялись одним и тем же правилом,
а не тремя копиями).

Здесь же нашёлся and исправлен структурный пробел: `continueChatWithLlm` на
каждом ходу вызывал `analyze()` и получал классификацию, но использовал её
только для RAG-роутинга — на шагах category/service сырой текст клиента
шёл в `continueChatWorkflow` без неё. Из-за этого «течёт труба под мойкой»
не матчилось ни с одной услугой (подстрочный матчер сравнивает текст с
названиями каталога дословно, а не понимает смысл) — ровно то, для чего и
существует LLM-извлечение на первом ходу, но оно не было прокинуто дальше.
Добавлен `ChatTurnGuidance` (`category`/`serviceType`) — та же классификация
из `analyze()`, прокинутая в `continueChatWorkflow` как ещё один кандидат,
который всё равно проходит ту же детерминированную проверку по каталогу.
Это не повторяет ошибку D-025 (там подставлялся сырой текст LLM напрямую в
ответ пользователю) — здесь LLM только предлагает значение, а
`matchServiceByName`/`classifyCategory` решают, годится ли оно.

**Слот — единственное принципиально новое поведение.** Сетка из 5–7 кнопок
не имеет разумного текстового аналога (клиент не будет печатать UUID слота).
`preferredDate`/`preferredTime` уже собираются свободным текстом до этого
шага, а `sortSlotsByPreference` уже умеет ранжировать реальную доступность
по близости к ним. Поэтому вместо списка кнопок ассистент предлагает
**один** ближайший слот прозой («Ближайшее свободное время — 6 августа,
09:00. Подходит?»), а детерминированный (не LLM) матчер да/нет
(`AFFIRMATIVE_PATTERN`/`NEGATIVE_PATTERN`) читает ответ: «да» — бронирует
именно этот слот через существующий `createBookingTurn` (SQL не менялся);
«нет» — возвращает на сбор даты, и та же пара `handlePreferredDate` →
`handlePreferredTime` переиспользуется для повторного предложения.

При реализации всплыли ещё два бага, оба пойманы скриптовой проверкой до
деплоя, не в проде: (1) повторное предложение слота после отказа пыталось
создать **второй** lead для того же диалога — SQL-защита `lead_id is null`
в `createLeadTurn` корректно это отклоняла; `handlePreferredTime` теперь
проверяет `data.leadId` и, если lead уже есть, просто пересчитывает и
предлагает слот заново, не создавая новую заявку. (2) в этой новой ветке
`completeLeadDataSchema` (обычный `z.object` без `.passthrough()`) молча
вырезал `leadId`/`publicNumber` при повторном парсинге данных — из-за чего
следующее «да» не находило заявку. Оба поля явно домержены обратно перед
сохранением.

Кнопки на `/chat` и в hero-виджете убраны из UI целиком
(`chat-client.tsx`, `hero-chat.tsx`, `use-chat-session.ts`) — поле ввода
теперь показывается всегда. Тип `ChatOption`/поле `options` в контракте не
удалены (не требовалось для устранения кнопок из интерфейса), просто больше
никогда не заполняются реальными данными.
